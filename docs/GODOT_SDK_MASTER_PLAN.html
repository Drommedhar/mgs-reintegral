01 / THE TARGET

What “complete” means

Everything visual is replaceable

Maps, moving machinery, characters, materials, textures, lights, particles, water, cameras, HUD, menus, Codec, overlays and movie presentation have explicit editor entry points. Cinematic-only locations are first-class scenes.

Ordinary Godot authoring

Use the Scene tree, Inspector, inherited scenes, resources, signals and AnimationPlayer. Basic replacements and attachments require no script. GDScript and GDExtension support advanced presentation.

Godot completion rule: no PS1 primitive/VRAM renderer supplies its final image. Rebuild legacy visual behaviors as Godot materials, effects and Controls. Original art, animation and movie data may still come from the player’s discs. Original appearance remains an authoring choice.

Native gameplay remains authoritative, as confirmed for this plan. Visual removal does not remove collision or alter scripts. Future gameplay replacement can be designed behind a separate simulation interface; this plan does not move gameplay into Godot.

Introduce a semantic bridge beside the existing primitive interface. Geometry and semantic data must exist before projection, camera rejection and PS1 packet creation. Publishing them must not depend on whether a legacy polygon would have been drawn.

ContractRequired behavior
ResourcesRegister meshes, materials, textures, rig definitions and local content references once. Publish revisions and changes. Keep original asset identity separate from actor instance identity.
Actor statePublish spawn/despawn, map membership, visibility, transforms, rig poses, named attachment anchors and typed properties. Initial snapshots make late attachment and reload correct.
Events & clockOrder events with simulation ticks and monotonic sequence numbers. Preserve events across pose coalescing; detect gaps and resynchronize. Pause, restart, cutscene skip and scene changes reset the appropriate visual history.

One coordinate contract: metres, Y up, documented handedness, transforms and camera projection. Adapt the current render-coordinate convention at the boundary and migrate older mods with a report. Preview and runtime use the same resolver and conversion code.

Keep the current x86 game / x64 Godot process separation. GDExtension libraries belong to the Godot process. A future gameplay provider would implement a separately versioned simulation contract; preserving that seam does not promise interchangeable gameplay today.

04 / THE FIRST COMPLETE EXAMPLE

Replace the elevator. Keep its native behavior.

The dock elevator is the first acceptance scene. The user clarified that the bars are the attached platform railing. Platform and railing must be separately editable targets sharing the verified native body motion and visibility. Other articulated actors expose independent anchors where native motion actually differs.

Parenting for movement

Select the elevator in the Scene tree, expand its published anchors, and place a custom mesh under the relevant anchor. Saved local offsets remain artist-owned. Native movement drives the anchor every simulation update.

05 / EASY MODDING

Open, edit, run, export, reopen.

  1. Choose or create a mod. Open its ZIP or existing workspace. Keep identity, version, dependency list and export destination visible; reopening resumes local work. Export remains an explicit Save action.
  2. Browse all presentation content. Maps, variants, cinematic-only sets, actors, models, textures, effects, UI and cameras share a searchable catalog with friendly names and stable IDs.
  3. Edit the composed scene. Local original references and authored changes appear together in the normal tree. Material edits, child parenting, visibility, transforms, Undo/Redo, duplicate and rename preserve bindings.
  4. Inspect dynamic content offline. Show actor templates and declared scenarios from local data. Mark conditional or unresolved placement explicitly. Preview states help authoring; only a native test session establishes live behavior.
  5. Run this scene from Godot. Choose a valid entry profile or checkpoint, launch the native game alongside the renderer, and enable the active workspace directly. Stop terminates both owned processes cleanly.
  6. Inspect and iterate. Select a live actor to locate its authored binding. Show current state, anchors, event history and unresolved references. Hot-reload supported visual resources; request a restart for native DLLs or incompatible changes.
  7. Export and share. Validate dependency closure, target bindings, API versions and renderer requirements. Package authored assets and changes. Reinstall into a fresh workspace using only that recipient’s local originals.

Two explicit test modes

Preview: editor-only lighting, animation scrubbing and representative UI/actor state.

Native test: actual gameplay, event delivery, collision, UI actions and original cutscene sequencing. Launch profiles store stage, disc, scenario/checkpoint and mod set. Raw stage entry must not pretend to supply missing story prerequisites.

Protect the editing loop

Test sessions use separate saves/settings by default. The launcher and editor call the same session service. Import and reimport regenerate baselines without overwriting authored work; changed or missing IDs receive a repairable migration report.

Godot run integration is an implementation task. Verify the pinned build’s EditorPlugin hooks; begin with a reliable separate game window and add embedded play only after focus/input behavior is qualified.

Resource ownership and mod composition

Store OriginalAssetRef references plus sparse property changes, removals and authored nodes. Preview caches may contain retail-derived data and stay local. Export traverses materials, textures, animations, UI atlases, fonts and scene dependencies; an edited copy of an original asset does not become an independently authored asset.

For camera edits, save authored keys or key changes against a local original timeline. For UI, save layout/theme changes and local original sprite references. Never export an unchanged imported timeline, embedded original mesh, atlas, font or movie through a nested resource.

Compose baseline → shared location edits → exact scenario edits, then resolve mod priority within each scope. Exact-scenario edits win over shared defaults. Append independent additions; competing replacements identify their winner and allow the user to change order. Show conflicts for actor roles, UI slots and camera clips. Required unresolved targets block that mod with a useful explanation.

07 / MAPS WITHOUT GAMEPLAY

Author the shot in Godot. Keep the native sequence.

All scene types in the catalog

Cinematic-only rooms, alternate geometry, intro sets, title/briefing stages and endings receive their own entries. Shared location edits use an explicit relationship table; stages with similar names do not automatically share geometry or overrides.

Each entry describes its available maps, actor declarations, clips and native entry requirements. Unresolved conditional actors remain visible as unresolved entries.

Editable camera tracks

Use Camera3D and AnimationPlayer/AnimationLibrary for position, target, roll and lens/FOV, with cut markers and optional Path3D handles. Preview original keys from local content; save only authored changes.

The archived MGSR implementation already contains these concepts. Adapt them and verify scale, coordinate axes, lens conversion, clip identity and exact frame mapping.

Native time is the source of truth. Sample camera tracks from the current native clip frame. Camera interpolation is editable within each shot; hard cuts reset temporal rendering history. Dialogue, actor animation, gameplay callbacks and clip completion retain native sequencing.

Editor scrubbing previews presentation only. Do not replay gameplay events when dragging the playhead. Full live seek needs a deterministic checkpoint/replay mechanism and is a separate enhancement. AnimationPlayer seeking itself does not reconstruct native state or deliver skipped events.

Edited cameras can reveal geometry culled by the original shot. Publish active scene geometry independently of original camera culling; Godot evaluates visibility for the authored camera. Preserve the gameplay camera separately for AI, interaction and other native behavior. Recompute view-dependent particles and screen effects from world-space semantics.

Playback has a clear camera owner: native default, authored clip override, or editor inspection camera. Skipping, aborting and finishing a clip return ownership correctly. Timeline duration and gameplay event retiming stay unchanged in this milestone.

Reuse evidence: archived DmoCameraTrack.cs, DmoTimeline.cs, StageCutsceneCameraPath.cs and DmoAnimationCompiler.cs. Those files use another import/runtime pipeline; direct copying would not establish compatibility.

08 / LAUNCHER & COMMUNITY

A renderer selector that can grow

Add an installed-renderer registry and a persistent selector. Legacy means the renderer shipped in 0.2, including its established enhancement options. Godot gets its own settings and mod profile. Community packages register through the same contract.

Godot modes, clarified 13 October: full Godot scene rendering is the default and must load the same composed map content, materials, declared lights and authored additions as the editor. Native gameplay still determines actor state and poses. An optional Legacy through Godot mode presents the native primitive visuals without scene lighting/PBR or Godot scene mods. It is separate from preserved Legacy 0.2 and does not relax the zero-legacy-image requirement for full Godot mode. Record startup/import/content verification timings separately from gameplay frame pacing.

The default map environment supplies a readable ambient level in both imported editor scenes and runtime. The original point lights alone do not reproduce the original game's overall illumination. Ambient color and energy belong to an ordinary editable Godot Environment resource; authored environment settings take precedence over the shared default.

For players

  • Select Legacy 0.2, Godot or an installed community renderer.
  • See supported settings and compatible mods for that renderer.
  • Keep save files and common gameplay settings available across selections.
  • Change renderer on the next launch; no live GPU-backend switching is required.
  • A failed renderer reports its error. Switching to Legacy is an explicit choice.

For renderer authors

  • A descriptor declares ID, version, entry point, platform/architecture, runtime compatibility and supported contract versions.
  • Capabilities describe semantic scenes, UI, cameras, effects, settings and optional legacy-command support.
  • A sample backend proves registration, handshake, input, presentation and shutdown without recompiling the launcher.
  • Compatibility tests and documented buffers replace dependencies on private native pointers.

Practical rollout: initially ship matching Legacy and Godot native executables behind launcher package descriptors, preserving the current build-time backend boundary. Next introduce one versioned native presentation host for external semantic renderers. The player-facing selector remains unchanged. A source-module contract is not presented as an already stable binary plugin ABI.

Renderer packages and content mods are distinct. Mods declare their required renderer features and dependencies; the launcher retains separate enabled sets and explains incompatible choices. A Godot-specific scene is not promised to work in every community renderer. Existing settings migrate to Legacy unless the user selects another backend.

Distribute the Godot runtime, editor SDK, native host and importer with compatible version metadata and relative paths. End users should not need the repository or a compiler. Native extension authors need a toolchain; ordinary scene, UI, material and script authors do not.

Migration policy: retain the current compositor only in development while categories are replaced. Track ownership for every category and count any legacy draw contribution. An incomplete Godot build is labeled experimental; missing features never silently choose legacy pixels. The finished Godot pipeline removes the primitive raster, ordering-bucket compositor and its metadata/depth workaround where no longer needed.

Audit native drawing functions for nonvisual side effects before bypassing them. Actor updates, palette state, video timing, resource lifetime, game readbacks and script callbacks must continue even when their old draw submission is disabled.

Performance is part of the architecture

Load immutable resources once; stream changed poses, states and events. Batch effects and reuse meshes/materials. Prepare likely shader variants during loading, avoid repeated full-resolution copies and measure CPU, GPU and bridge time separately. Preserve motion vectors and reset temporal history on cuts, teleports and reloads.

Target stable 60-class presentation under the native 59.94 Hz clock: 16.683 ms per presentation without changing gameplay timing. FSR2 remains available. Evaluate 1440p on the local RX 9070 XT with a recorded graphics preset and no competing game. Report all frame times, loading separately and active-cutscene spikes explicitly; average FPS alone cannot pass acceptance. RT/Jenova is outside this plan.

10 / DELIVERY SEQUENCE

Prove the workflow before scaling it across the game

Each milestone ends in an editable example, a packaged artifact where applicable, and recorded acceptance evidence. This is a dependency plan with relative effort; dates require the first contract and actor investigations.

M0 · Baseline→M1 · Contracts→M2 · Elevator→M3 · Edit / run→M4 + M5 + M6→M7 · Coverage→M8 · Release

Expand milestones for implementation scope and exit gates.

M0Baseline, coverage inventory and target contracts

Small–medium Preserve the working 0.2 renderer and current Godot branch. Record the pending FSR2 changes independently; establish a reproducible build and performance baseline.

  • Inventory every native presentation producer: geometry, actors, UI, effects, movies, cameras and readbacks. Record coverage by stage/scenario, not just resource counts.
  • Map the actual dock elevator platform/bar outputs and script provenance. Inventory native UI state owners and drawing side effects.
  • Freeze the plan’s identity, coordinate, ownership and event-ordering rules as versioned schemas and design examples. Replace stale readiness statements in existing docs.

Exit: Legacy 0.2 remains reproducible; missing categories and their native source owners are known; the elevator and UI contracts can be reviewed against actual native state.

M1Presentation bridge and selectable renderers

Large Depends on M0. Add retained resources, actor lifecycle, typed state/events, UI models, clock and command acknowledgements without moving simulation ownership.

  • Introduce renderer/session descriptors and runtime negotiation; adapt Godot behind the new boundary while preserving the current path for comparison.
  • Add launcher discovery, Legacy/Godot selection, per-renderer settings and mod compatibility. Start with matched executables, then expose the generic semantic host.
  • Test stage reset, repeated actor IDs, reconnect/full state, ordered events and input ownership. Add an asset-free external sample renderer for contract checks.

Exit: one launcher starts either established Legacy or Godot, preserves common saves/settings and loads an external renderer descriptor without a launcher rebuild. Protocol mismatch fails clearly.

M2Dynamic actor bindings: the dock elevator

Large · first user-facing proof Depends on M1. Implement stable bindings, separate body/bar anchors, property binding and state/event inspection.

  • Publish verified native movement and per-part visibility. Add editor placeholders, artist-owned children and visual suppression of original parts.
  • Ship an asset-free elevator example: custom platform and bars, attached lamp, state-driven indicator and optional GDScript reaction.
  • Verify pause, reload, attach-late, despawn/reuse, undo/redo and ZIP round-trip. Keep all collision and native elevator behavior intact.

M3Editor workspace, native run and mod composition

Medium–large Depends on M1/M2. Finish one reliable editing loop before multiplying stage-specific adapters.

  • Unify map, actor, effect, material, texture, UI and clip catalogs; replace hardcoded map choices with content metadata.
  • Add Preview and Run Native actions, launch profiles/checkpoints, workspace mounting, controlled hot reload, stop/cleanup and live-to-authored selection.
  • Use the same composition resolver in editor/runtime. Add conflict view, reimport migration, original-resource dependency checks and multi-mod validation.

M4Godot world effects and complete image ownership

Very large Depends on M1–M3. Replace each compatibility category with semantic inputs and editable Godot resources.

  • Migrate runtime-textured geometry, special vision/stealth, palette animation, water/particles, screen effects and video presentation in measured batches.
  • Export camera-independent active geometry and poses; fix temporal motion/history for moving characters, mechanical actors and cuts.
  • Implement required visual readbacks; remove redundant world composites as ownership moves. UI removal completes jointly with M5.

  • Rebuild the original layout as reusable Controls and Themes. Expose individual UI replacement slots and whole-interface replacements. Save/load uses a flat PC save list and New Save while keeping the original fonts, colors and framing; native memory-card storage remains underneath.
  • Connect launcher, native runtime, renderer and mod settings through one registry; support keyboard/controller focus, localization and display apply/revert.

  • Expose isolated cutscene locations, scenario relationships and exact overrides. Add timeline preview, lens/roll editing, hard cuts and clip selection.
  • Sample authored tracks from native time; preserve event/audio timing and implement clean skip/abort/completion camera handoff.

M7Campaign coverage, bindings and frame pacing

  • Classify missing authoring data explicitly; provide verified entry profiles and focused transition checks. Human playthrough supplies broader acceptance.
  • Resolve remaining shadow-preparation/cutscene hitches, large uploads and first-use work. Test long sessions, repeated loading and temporal effects on declared hardware/presets.

  • Validate on a clean user profile: local disc import, renderer selection, ZIP install/edit/export/reinstall, language resources and save continuity.

12 / DECISIONS & BOUNDED INVESTIGATIONS

What is decided, and what needs a prototype

Confirmed by the user

  • Native gameplay remains authoritative for now.
  • Default UI follows the original layout using editable Godot Controls.
  • Godot must own all visuals; Legacy 0.2 remains selectable.
  • Dynamic objects, cinematic-only maps, UI and camera tracks belong in the authoring scope.
  • Easy modding, direct editor testing and community renderer extensibility are design goals.

Proposed scope boundaries

  • Renderer changes require restarting the session.
  • First camera milestone edits presentation at unchanged native clip times.
  • Offline scrubbing and live gameplay execution are separate modes.
  • Visual node transforms/removals preserve native collision.
  • Keep original rig compatibility first; general retargeting is a later API expansion.
